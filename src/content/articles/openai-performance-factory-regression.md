ChatGPT 的首个 Token 延迟升高，值班工程师收到一条报警。延迟的起点是什么？哪些请求受影响？新版本与慢请求之间有什么证据？

OpenAI 工程师 Okay Zed 和 Cyrus Forbes 的 11 月 19 日文章介绍了 **Performance Factory**。首条性能回退流程的运行时间是三个月出头，跟踪 **1700 多次调查**，定位 **600 多起根因**。作者给出的日均调查量是 **17 次**。这些数字统计调查与根因定位，故障修复的验收依据是生产指标。[1]

## 任务记录承担交接

OpenAI 的团队积累了 30 多项性能工具。`perf-forensics` 技能记录常见排查步骤和工具用法。早期的云端调查结论发往 Slack，工程师承担补丁和上线验证。报警线程的数量增加了筛选工作。[1]

性能工厂的基本单位是一张任务单。任务保存状态、关键发现和下一步责任。审查者需要的是受影响的请求、因果证据和变更风险。部署验证者需要的是旧基线、观察指标和部署状态。[1]

任务服务定义状态与流转规则，调度循环分派就绪的步骤，云端 Codex 执行调查和修改。事件订阅响应 PR 评论、CI 失败或部署完成等信号，等待中的任务恢复执行资格。[1]

这种安排有一个直接的工程收益。等待代码审查的几个小时属于任务生命周期，执行资源消耗来自实际运行的工作。任务状态的独立保存，使核对结论和复跑某一阶段具备可操作性。

![性能回退工作流，报警建单、定位和复核、提补丁、人工审查、生产验证](/article-images/openai-performance-factory-regression/regression-loop.webp)

*根据 OpenAI 描述绘制。无改善的任务返回调查，部分恢复的残留问题获得新任务。*[1]

## 诊断的第二个 Agent 专门找反证

报警阈值的触发时刻与性能下降的起点是两个时间。调查范围包含受影响的请求、同类请求的延迟变化和慢请求的占比变化。部署记录、功能开关、日志和调用链提供因果证据。[1]

OpenAI 记录过一次图像请求失败。调查 Agent 怀疑负责定位文件的内部服务。审查 Agent 发现，文件定位服务恢复，图像请求的失败持续。原诊断缺少对持续失败的解释，审查 Agent 重开调查。[1]

作者披露了一次人工复核。样本为 **100 条根因建议**，其中 **70%** 获评准确，其余需要补充或缺少充分的因果证据。这个比例的分母是根因建议，线上恢复是另一项验收。[1]

## 合并 PR 和恢复指标是两个状态

根因复核通过是提补丁的条件。Codex 实现修改并提交 PR，补丁审查检查根因覆盖和副作用。工程师决定是否合并和发布。缓存方案的取舍包括延迟收益和数据过期的风险。[1]

部署事件触发生产验证。指标回到基线，任务结案。指标部分恢复，原任务结束，残留问题进入新任务。指标没有改善，调查重开。这个分支设计保留了旧假设，也给剩余问题留下独立的证据链。[1]

一个可迁移的设计是给验收设定指标条件。总体平均耗时和受影响用户的尾部延迟属于两个指标。相同请求类型的对照需要基线和观察窗口，其他关键指标用于检查成本转移。

## 调查质量和交接质量各有评测

OpenAI 的调查评测使用历史生产事故。评估目标包含问题起点、影响程度、受影响请求和根因证据。事故结论和旧运行记录会泄露答案，历史测试的关键工作是限定可见证据。交接摘要则使用任务快照，评估陌生工程师能否理解影响和下一步依据。[1]

团队的检查清单包含调查工具故障和权限错误。重复阻塞调查的工具问题触发修复任务，工程师负责审核变更。主动发现未触发警报的性能问题，属于文章描述的后续方向。[1]

合并记录回答补丁是否进入主分支，部署记录回答改动是否上线。用户请求的指标是否恢复，需要生产验证。
